Spring Caching & Redis

Eliminate redundant database calls with Spring's Cache Abstraction. From simple @Cacheable to Redis-backed distributed caches with TTL, cache-aside patterns, and stampede prevention — production-grade caching done right.

1. Definition

Simple English

Imagine a waiter who memorizes your regular order. The first time you visit, they go to the kitchen (DB) and bring your food. Next time, they remember and serve you instantly. Caching does exactly this for your application — storing frequently accessed data in fast memory.

Technical

Spring's Cache Abstraction provides a unified API (CacheManager, Cache) that decouples caching logic from implementation. Annotations like @Cacheable are AOP-driven — Spring intercepts the method call, checks the cache, and only invokes the method on a cache miss. Redis is the most common distributed cache backend.

Purpose

Reduce database load by 80–99% for read-heavy workloads. Sub-millisecond Redis reads replace 10–50ms database queries. Critical for scaling: the database is usually the first bottleneck in a growing system.

2. The Cache-Aside Pattern Flow

@Cacheable — Cache-Aside (Lazy Loading)

Incoming Request — getProduct(id: 42)
Spring AOP intercepts @Cacheable method

Checks Redis for key "products::42"

✓ Cache HIT

Return cached object directly. Method never invoked. ~0.5ms response time.

✗ Cache MISS

Invoke the actual method → query DB → store result in Redis with TTL → return result.

Key Guarantee: After a miss, subsequent requests for the same key are served from Redis until TTL expires.

3. Real-World Project Example

E-Commerce Product Catalog

10,000 product reads per second, database stays at rest.

@Cacheable — Read: Product Detail Pages

@Cacheable(value="products", key="#id") on getProductById(Long id). Product pages are read thousands of times per minute. After the first DB fetch, all subsequent reads come from Redis in ~0.3ms — vs 25ms DB query.

@CachePut — Write: Admin Updates Product

@CachePut(value="products", key="#product.id") on the update method. Unlike @Cacheable, this ALWAYS calls the method AND updates the cache — ensuring the cache is immediately consistent after an admin edit.

@CacheEvict — Delete: Product Removed

@CacheEvict(value="products", key="#id") on delete. Removes the specific entry from Redis immediately. Use allEntries=true for cache-bust-all scenarios like bulk price updates.

4. 7 Key Points For senior-level depth

1

Annotation Comparison

@Cacheable — read-through (only calls method on miss). @CachePut — always calls method AND updates cache (for write-through). @CacheEvict — removes one or all entries. @Caching — combines multiple cache operations on one method.

2

@Cacheable Only Works on Public Methods

Because caching is AOP-based (via a CGLIB proxy), it only works on public methods called from outside the bean. Calling a @Cacheable method from within the same class bypasses the proxy and the cache entirely — a very common mistake in production.

3

Cache Stampede (Thundering Herd)

When a popular cache entry expires, hundreds of concurrent requests simultaneously miss the cache and hit the DB at once. Solutions: Probabilistic early expiration, Redis SETNX locking (one request rebuilds the cache, others wait/return stale), or Caffeine's async refresh.

4

TTL (Time-To-Live) Strategy

Set appropriate TTLs per cache: product catalog = 10 minutes (acceptable staleness), user session = 30 minutes, exchange rates = 30 seconds. Configure per-cache TTLs in RedisCacheConfiguration using entryTtl(Duration.ofMinutes(10)).

5

Cache Keys with SpEL

Cache keys are defined with Spring Expression Language (SpEL). key="#userId + '-' + #type" builds compound keys. Use condition="#price > 100" to cache only expensive operations. Use unless="#result == null" to avoid caching null results.

6

Local vs Distributed Cache

ConcurrentHashMap / Caffeine: in-process, zero latency, lost on restart, not shared between nodes. Redis: network hop (~0.3ms), survives restarts, shared across all app instances. For microservices and horizontally scaled apps, Redis is required.

7

What Happens If Redis Goes Down?

By default, if Redis is down, Spring's RedisCacheManager throws an exception on cache operations, potentially causing method failures. Configure a CacheErrorHandler to gracefully degrade: on cache failure, simply skip the cache and go directly to the database. Your app continues serving requests, just slower.

/* 1. pom.xml — add Redis starter */
// <dependency>
//   <groupId>org.springframework.boot</groupId>
//   <artifactId>spring-boot-starter-data-redis</artifactId>
// </dependency>

/* 2. Redis Cache Configuration — JSON serialization + per-cache TTL */
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public RedisCacheManagerBuilderCustomizer cacheCustomizer() {
        return builder -> builder
            .withCacheConfiguration("products",
                RedisCacheConfiguration.defaultCacheConfig()
                    .entryTtl(Duration.ofMinutes(10))
                    .disableCachingNullValues()
                    .serializeValuesWith(RedisSerializationContext
                        .SerializationPair.fromSerializer(
                            new Jackson2JsonRedisSerializer<>(Object.class)))
            )
            .withCacheConfiguration("users",
                RedisCacheConfiguration.defaultCacheConfig()
                    .entryTtl(Duration.ofMinutes(30)));
    }
}

/* 3. Service with caching annotations */
@Service
public class ProductService {

    private final ProductRepository repo;

    // Cache HIT: return from Redis (method never called)
    // Cache MISS: call DB, store in Redis with 10min TTL
    @Cacheable(value = "products", key = "#id", unless = "#result == null")
    public Product getById(Long id) {
        return repo.findById(id).orElse(null);
    }

    // Always calls DB update AND refreshes cache
    @CachePut(value = "products", key = "#product.id")
    public Product update(Product product) {
        return repo.save(product);
    }

    // Remove from cache on delete
    @CacheEvict(value = "products", key = "#id")
    public void delete(Long id) {
        repo.deleteById(id);
    }

    // Bust entire products cache (e.g., bulk price update)
    @CacheEvict(value = "products", allEntries = true)
    public void bulkPriceUpdate() { ... }
}

7. Senior Developer Answer

"We use Spring's Cache Abstraction with Redis as the distributed backend across all our horizontally-scaled microservices. The abstraction layer means we can swap from Caffeine in unit tests to Redis in production without changing business code.

On the implementation side, I configure Jackson2JsonRedisSerializer over the default Java serializer — it's human-readable, version-tolerant, and non-Java services can consume the same cached data. I set per-cache TTLs matched to data staleness tolerance: 10 minutes for product catalog, 30 seconds for pricing.

The critical gotcha I always mention: @Cacheable is AOP-based, so it's completely bypassed when called within the same class (self-invocation). I've seen this cause subtle bugs where developers add caching to a private or internal method and wonder why the cache is never populated.

For cache stampede protection on high-traffic keys, we implement a Redis SETNX-based lock: the first thread to miss the cache acquires a short-lived lock to rebuild it, while other threads either wait or return a slightly stale value — preventing the thundering herd from pounding the database."
