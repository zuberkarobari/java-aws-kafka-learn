Environment Config

Profiles & Externalized Config

How Spring Boot manages configuration for dev, staging, and production environments without changing code — using profiles, @ConfigurationProperties, and environment variable overrides aligned with the 12-Factor App methodology.

1. Definition

Simple English

Profiles are like "modes" for your app — "dev mode" connects to your local database, "prod mode" connects to AWS RDS. You switch modes by changing a single environment variable, not the code. No more hard-coded DB URLs.

Technical

Spring Profiles allow registering beans and configuration conditionally. application-{profile}.yml files are merged over the base config when a profile is active. External config sources (env vars, system properties) follow a strict property source precedence order.

Purpose

Implements the 12-Factor App principle: "Store config in the environment." Enables the same Docker image to run in dev, staging, and production by injecting config externally — critical for Kubernetes/cloud deployments.

2. Property Source Precedence Order

When the same property is defined in multiple places, Spring Boot resolves it using this priority (highest wins):

Priority Stack (Top = Wins)

① Command-line arguments -- --server.port=9090
② OS Environment Variables SPRING_DATASOURCE_URL=...
③ System Properties -Dserver.port=8081
④ application-{profile}.yml application-prod.yml overrides base
⑤ application.yml (base) Lowest priority config file
⑥ @PropertySource / Defaults Inline defaults in code
Key Insight: Environment variables always override application.yml — this is how Kubernetes ConfigMaps and Secrets inject config at runtime without rebuilding the Docker image.

3. Real-World Project Example

Deploying to Kubernetes

The same Spring Boot JAR deployed to 3 environments, zero code changes.

Local Dev — application-dev.yml

Developer runs SPRING_PROFILES_ACTIVE=dev. Spring loads application-dev.yml on top of base config: H2 in-memory database, debug logging, mock payment service wired via @Profile("dev").

Production K8s — Environment Variables

The Kubernetes Deployment spec sets SPRING_PROFILES_ACTIVE=prod and injects secrets via SPRING_DATASOURCE_PASSWORD from a Kubernetes Secret. The app never sees these values in code — they're injected at runtime by the orchestrator.

Zero Secrets in Git

Sensitive values (DB passwords, API keys, JWT secrets) are NEVER in application.yml. They're injected via environment variables, Kubernetes Secrets, AWS SSM Parameter Store, or HashiCorp Vault — keeping your codebase audit-safe.

4. 7 Key Points For senior-level depth

1

@ConfigurationProperties over @Value

Prefer @ConfigurationProperties(prefix="app") over @Value("${app.timeout}") for grouped config. It binds an entire prefix to a typed POJO with validation support (@Validated), IDE auto-completion, and refactoring safety. Use @Value only for single, isolated properties.

2

Profile-Specific Beans

Use @Profile("dev") on a @Bean or @Configuration class to register it only when that profile is active. Common pattern: a @Profile("dev") MockPaymentService vs a @Profile("prod") StripePaymentService — same interface, different implementations.

3

Environment Variable Naming

Spring Boot auto-converts environment variable naming conventions. spring.datasource.url in YAML maps to SPRING_DATASOURCE_URL as an env var. Dots become underscores, camelCase becomes SNAKE_CASE (Relaxed Binding). This is how Kubernetes env vars map to YAML properties.

4

Never Put Secrets in application.yml

Committing secrets to Git is a critical security risk. The correct pattern: use application.yml for non-sensitive defaults, inject secrets at runtime via environment variables or a secrets manager (AWS SSM, HashiCorp Vault, Kubernetes Secrets).

5

Multiple Active Profiles

You can activate multiple profiles simultaneously: SPRING_PROFILES_ACTIVE=prod,metrics,kafka. Properties from all active profile files are merged. If the same key exists in multiple active profile files, the last one in the list wins.

6

@ConfigurationProperties Validation

Add @Validated to your @ConfigurationProperties class and JSR-380 annotations on fields. Spring validates at startup — app fails to start if app.timeout is negative. This gives you a safe, fail-fast config contract.

7

Spring Cloud Config (Centralized Config)

For microservice architectures with 10+ services, each needing per-environment config, Spring Cloud Config Server centralizes all configuration in a Git repo. Microservices fetch their config at startup via HTTP. Combined with Spring Cloud Bus, config changes can be pushed to all services without restart (dynamic refresh via @RefreshScope).

# application.yml — base config (non-sensitive defaults)
server:
  port: 8080

app:
  payment:
    timeout-ms: 3000
    max-retries: 3

---
# application-dev.yml — overrides for local development
spring:
  datasource:
    url: jdbc:h2:mem:devdb
    driver-class-name: org.h2.Driver
logging:
  level:
    com.example: DEBUG

---
# application-prod.yml — non-secret overrides (secrets via env vars)
spring:
  datasource:
    url: jdbc:postgresql://prod-db.internal:5432/appdb
    driver-class-name: org.postgresql.Driver
    # password injected via env: SPRING_DATASOURCE_PASSWORD
logging:
  level:
    root: WARN

/* 1. Type-safe @ConfigurationProperties POJO */
@Configuration
@ConfigurationProperties(prefix = "app.payment")
@Validated
public class PaymentProperties {

    @Positive(message = "Timeout must be positive")
    private int timeoutMs;

    @Min(1) @Max(10)
    private int maxRetries;

    // getters + setters (or use Records in Spring Boot 3.2+)
}

/* 2. Profile-specific bean registration */
@Profile("dev")
@Component
public class MockPaymentService implements PaymentService {
    @Override
    public PaymentResult charge(ChargeRequest req) {
        return PaymentResult.success("MOCK-TXN-001"); // No real calls
    }
}

@Profile("prod")
@Component
public class StripePaymentService implements PaymentService {
    private final PaymentProperties props;
    // Uses real Stripe API with injected timeout config
}

7. Senior Developer Answer

"Our externalized config strategy follows the 12-Factor App strictly: code is environment-agnostic, config flows in at runtime. We maintain application.yml for safe defaults, and application-{env}.yml for environment-specific non-sensitive overrides.

Secrets never touch source control. In Kubernetes, our Deployment manifests reference Kubernetes Secrets as environment variables — Spring Boot's relaxed binding automatically maps SPRING_DATASOURCE_PASSWORD to spring.datasource.password.

For type-safe config, I strongly prefer @ConfigurationProperties over @Value. We add @Validated to config properties classes with JSR-380 constraints so the app fails fast at startup with a clear error if a required config is missing or invalid — catching config drift early in CI pipelines rather than discovering it in production."
