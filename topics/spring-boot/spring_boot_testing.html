Spring Boot Testing

The most asked non-trivial Spring Boot topic in 2026 interviews. Master the testing pyramid: unit tests with Mockito, slice tests with @WebMvcTest and @DataJpaTest, and full integration tests with @SpringBootTest and TestContainers.

1. The Testing Pyramid

Spring Boot Test Types — Choose the Right Scope

@SpringBootTest — Full Integration Test

Loads entire ApplicationContext. Slow (30s+). Test critical user flows end-to-end with a real DB (TestContainers). Few tests.

@WebMvcTest

Controller layer only. No service/DB wired. Uses MockMvc. Fast.

@DataJpaTest

JPA layer only. In-memory H2 or TestContainers. Tests queries & mappings. Fast.

Plain JUnit 5 + Mockito — Unit Tests

No Spring context. Mock all dependencies. Fastest (milliseconds). Most tests live here. Tests one class in isolation.

Rule of thumb: 70% unit tests → 20% slice tests → 10% integration tests. More integration tests = slower CI pipeline.

The right test for each layer of the same feature.

4. 7 Key Points For senior-level depth

1

@MockBean vs @Mock

@Mock is pure Mockito — no Spring context involved. Used in plain unit tests with @ExtendWith(MockitoExtension.class). @MockBean creates a Mockito mock AND replaces the real Spring bean in the application context. Use @MockBean in @WebMvcTest/@SpringBootTest, @Mock in unit tests.

2

@DataJpaTest — Transactional by Default

Every @DataJpaTest test method runs in a transaction that is automatically rolled back after the test. This means tests don't pollute each other with stale data. Use @Commit or @Rollback(false) only if you explicitly want data to persist between tests (rare).

3

TestContainers — Real DB in Tests

TestContainers starts actual Docker containers (PostgreSQL, Redis, Kafka) for your tests, then tears them down. Unlike H2 (which can mask DB-specific SQL dialect issues), TestContainers tests against the same database engine as production — finding bugs that H2 silently ignores.

4

@SpringBootTest is Slow — Use it Sparingly

Every time @SpringBootTest loads with a different configuration (different @MockBean combinations), Spring creates a NEW application context — each one takes 3–30 seconds. Keep @SpringBootTest configuration consistent across tests to enable context caching and reuse the same context across multiple test classes.

5

Testing Security with @WithMockUser

In @WebMvcTest, Spring Security is active by default. Use @WithMockUser(roles = "ADMIN") to simulate an authenticated user in your test without going through the full login flow. Use @WithAnonymousUser to test unauthorized access.

6

Testing Async Methods

For @Async methods, use CompletableFuture.get() to block until completion in tests, or use Awaitility for event-driven assertions: await().atMost(5, SECONDS).until(() -> verify(service).processOrder(any())). Awaitility polls the condition until it's true or times out.

7

@RestClientTest for HTTP Clients

Testing components that call external REST APIs? Use @RestClientTest to load only the HTTP client and configure a MockRestServiceServer that intercepts HTTP calls and returns canned responses — without actually making network requests. Tests both happy path and error handling (timeouts, 500s) in milliseconds.

/* 1. UNIT TEST — No Spring context. Pure Mockito. */
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock OrderRepository orderRepo;
    @Mock InventoryService inventoryService;
    @InjectMocks OrderService orderService;

    @Test
    void shouldThrowWhenOutOfStock() {
        given(inventoryService.getStock("PROD-1")).willReturn(0);

        assertThatThrownBy(() -> orderService.placeOrder("PROD-1", 5))
            .isInstanceOf(InsufficientStockException.class);

        verify(orderRepo, never()).save(any()); // Never saved
    }
}

/* 2. SLICE TEST — @WebMvcTest loads MVC layer only */
@WebMvcTest(OrderController.class)
class OrderControllerTest {

    @Autowired MockMvc mockMvc;
    @MockBean OrderService orderService; // Replaces real service bean

    @Test
    @WithMockUser(roles = "USER")
    void shouldReturn400WhenBodyInvalid() throws Exception {
        mockMvc.perform(post("/api/orders")
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"productId\": null}")) // Invalid body
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.violations.productId").exists());
    }
}

/* 3. INTEGRATION TEST — TestContainers + real PostgreSQL */
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers
class OrderIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16");

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired TestRestTemplate restTemplate;

    @Test
    void fullOrderFlow() {
        var request = new CreateOrderRequest("PROD-1", 2);
        var response = restTemplate.postForEntity("/api/orders", request, Order.class);

        assertThat(response.getStatusCode()).isEqualTo(HttpStatus.CREATED);
        assertThat(response.getBody().getId()).isNotNull();
    }
}

7. Senior Developer Answer

"My testing philosophy for Spring Boot follows a strict pyramid. The majority of tests are plain JUnit 5 + Mockito unit tests — no Spring context, no annotations, just fast feedback on business logic. These run in under 100ms total and form the safety net for refactoring.

For the web layer, I use @WebMvcTest with @MockBean for the service. This validates HTTP contract — routing, validation, serialization, and security rules — without loading JPA or touching a database. It's 5–10x faster than @SpringBootTest.

For critical integration paths (order placement, payment processing), I use @SpringBootTest with TestContainers running actual PostgreSQL. H2 masks too many dialect-specific bugs. I also use @DynamicPropertySource to point the app at the container's JDBC URL.

The biggest mistake I see: overusing @SpringBootTest. Every unique combination of @MockBeans creates a new context — a project with 50 integration tests can have 10 seconds of startup per unique context. I enforce that all integration tests use a shared base class with the same @MockBean configuration to maximize Spring's context caching."
