Spring Bean Lifecycle

Every Spring bean is born, lives, and dies under IoC container control. Understanding the full lifecycle — instantiation, dependency injection, post-processing, initialization, and destruction — is a senior-level must-know.

1. Definition

Simple English

Think of a bean's lifecycle like hiring a new employee: HR (Spring) recruits them, trains them (injects dependencies), onboards them (runs @PostConstruct), then they do their job, and finally they retire gracefully (@PreDestroy cleanup).

Technical

The Spring bean lifecycle is the sequence of phases that the IoC container orchestrates for every managed bean: class loading, instantiation, property population, BeanPostProcessor callbacks, custom init logic, ready state, and eventually destruction callbacks.

Purpose

Gives developers well-defined hooks to run custom logic at precise lifecycle moments — opening DB connections post-init, validating config, registering listeners, and releasing resources on shutdown — without Spring coupling in your code.

2. The Complete Lifecycle Flow

Spring Bean Lifecycle — Phase by Phase

① Instantiation

Spring calls new MyBean() via reflection (constructor injection) or a factory method.

② Property Population (Dependency Injection)

Spring injects all @Autowired dependencies, @Value fields, and other property values.

③ Aware Interface Callbacks

If bean implements BeanNameAware, BeanFactoryAware, or ApplicationContextAware, Spring calls those setters to inject container references.

④ BeanPostProcessor — postProcessBeforeInitialization()

All registered BeanPostProcessors get a chance to wrap or modify the bean BEFORE init. Spring's AOP proxy creation happens here.

⑤ Initialization Callbacks (Your Code Runs Here)

Three options (in order): afterPropertiesSet() (InitializingBean), @PostConstruct method, or initMethod attribute in @Bean.

⑥ BeanPostProcessor — postProcessAfterInitialization()

Post-processors can still modify the bean AFTER initialization. This is the final chance before the bean is handed to clients.

⑦ Bean is READY — Serves Application Requests

The fully initialized bean is placed in the singleton cache and injected wherever needed.

⑧ Destruction Callbacks (Application Shutdown)

On context.close(): @PreDestroy, then destroy() (DisposableBean), then destroyMethod. Close DB connections, thread pools, etc.

3. Real-World Project Example

Database Connection Pool Service

How lifecycle hooks power real enterprise initialization and cleanup.

@PostConstruct — Open Resources

A DataSourceHealthChecker service annotates a method with @PostConstruct. After all properties are injected, Spring calls this method to establish a test DB connection, verifying the datasource URL is valid before the app serves any traffic.

BeanPostProcessor — AOP Proxies

When you put @Transactional on a service, Spring's AnnotationAwareAspectJAutoProxyCreator (a BeanPostProcessor) wraps your bean in a CGLIB proxy after initialization, transparently adding transaction boundary logic.

@PreDestroy — Release Resources

A KafkaConsumerManager uses @PreDestroy to gracefully call consumer.close() when the Spring context shuts down — preventing consumer group rebalancing storms and uncommitted offset loss.

4. 7 Key Points For senior-level depth

1

@PostConstruct vs Constructor

Constructor runs before DI. If your init logic needs injected dependencies (e.g., a repository to fetch config), it must go in @PostConstruct, not the constructor — because dependencies aren't set yet when the constructor runs.

2

BeanPostProcessor vs BeanFactoryPostProcessor

BeanPostProcessor operates on bean instances (after creation). BeanFactoryPostProcessor operates on the bean definitions (metadata) before any beans are instantiated — used by PropertySourcesPlaceholderConfigurer to resolve ${} placeholders.

3

Init Method Priority Order

When multiple init hooks are defined, the order is strict: ① @PostConstruct → ② afterPropertiesSet() (InitializingBean) → ③ @Bean(initMethod). Destruction order reverses this.

4

Prototype Beans Have No Destroy

Spring does NOT call @PreDestroy on Prototype beans. Once handed to the client, the container forgets about it. If a Prototype holds resources (connections, files), you must manage cleanup yourself — a common interview gotcha.

5

SmartLifecycle for Ordering

For complex shutdown ordering (e.g., stop Kafka consumers before closing DB connections), implement SmartLifecycle. The getPhase() method returns an integer — higher phase number starts later and stops first.

6

@DependsOn for Ordering

Use @DependsOn("cacheService") to ensure a bean is initialized only after another specific bean. Useful when there's no direct DI relationship but an implicit ordering requirement.

7

ApplicationContext Refresh Events

After all beans are initialized, the context publishes a ContextRefreshedEvent. You can listen for this via @EventListener to run one-time startup logic that requires ALL beans (including lazy ones) to be available — e.g., warming up caches after the full context is ready.

6. Complete Code Example

BeanLifecycleDemo.java

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.beans.factory.InitializingBean;
import org.springframework.beans.BeansException;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.stereotype.Component;

/* 1. The Bean — demonstrating all lifecycle hooks */
@Component
public class CacheWarmupService implements InitializingBean {

    private final ProductRepository repo; // Injected by Spring

    // ① Constructor — dependencies NOT yet set for @Autowired fields
    public CacheWarmupService(ProductRepository repo) {
        this.repo = repo;
        System.out.println("[1] Constructor called");
    }

    // ② @PostConstruct — all dependencies are now injected ✅
    @PostConstruct
    public void warmUpCache() {
        System.out.println("[2] @PostConstruct: loading hot products into cache");
        repo.findTop100ByOrderBySalesDesc()
            .forEach(p -> cache.put(p.getId(), p));
    }

    // ③ InitializingBean (runs after @PostConstruct)
    @Override
    public void afterPropertiesSet() {
        System.out.println("[3] afterPropertiesSet(): verifying cache health");
    }

    // ④ @PreDestroy — graceful shutdown
    @PreDestroy
    public void flushCache() {
        System.out.println("[4] @PreDestroy: flushing cache to disk");
        cache.clear();
    }
}

/* 2. Custom BeanPostProcessor — wraps every bean for logging */
@Component
public class LoggingBeanPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) {
        System.out.println("Before init: " + beanName);
        return bean; // Must return bean (or a proxy)
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        System.out.println("After init: " + beanName + " → READY");
        return bean;
    }
}

7. Senior Developer Answer

"The Spring bean lifecycle has several distinct phases that I leverage in production. After instantiation and dependency injection, Spring invokes BeanPostProcessor.postProcessBeforeInitialization() on all processors — this is where AOP proxy creation happens, which is why @Transactional works transparently. Then initialization hooks run in order: @PostConstruct, then afterPropertiesSet(), then the initMethod.

In practice, I use @PostConstruct to warm caches or validate configs that need injected services — you can't do this in a constructor because dependencies aren't set yet. For graceful shutdown, I use @PreDestroy to close Kafka consumers and thread pools before the context dies.

The most important distinction I emphasize is between BeanPostProcessor and BeanFactoryPostProcessor — the former operates on bean instances (used by AOP), while the latter operates on bean definitions before instantiation (used by Spring to resolve ${property} placeholders). Mixing them up is a common senior interview mistake."
