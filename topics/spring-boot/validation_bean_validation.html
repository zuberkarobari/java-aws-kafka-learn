Bean Validation

Validating incoming data at the API boundary using JSR-380 (Bean Validation 3.0), Hibernate Validator, @Valid vs @Validated, and building custom constraint validators — all production-grade patterns.

1. Definition

Simple English

Validation is the security guard at the entrance of your REST API. Before any business logic runs, it checks that all the required data is present, in the right format, and within acceptable bounds — rejecting bad input immediately.

Technical

Spring Boot integrates with the Bean Validation API (JSR-380) via Hibernate Validator. Annotations like @NotNull, @Size, and @Email on model fields, combined with @Valid on controller method parameters, trigger automatic validation before method execution.

Purpose

Prevents invalid data from ever reaching service or database layers. Centralizes validation rules on DTOs — keeping controllers thin and services focused on business logic, not defensive null-checks.

4. 7 Key Points For senior-level depth

1

@Valid vs @Validated

@Valid is JSR-380 standard — triggers validation but supports no groups. @Validated is Spring-specific — adds validation group support, letting you apply different constraints in create vs update scenarios. It also enables method-level validation in @Service classes.

2

Cascaded Validation with @Valid

If a DTO contains a nested object (e.g., AddressDTO address), annotate the field with @Valid to trigger validation recursively into the nested object's constraints. Without @Valid on the field, nested constraints are silently ignored.

3

Custom ConstraintValidator

For business-specific rules (e.g., "email must not already exist"), create a custom annotation + a class implementing ConstraintValidator<YourAnnotation, String>. Spring auto-detects it and can even inject repositories for DB lookups inside the validator.

4

@NotNull vs @NotBlank vs @NotEmpty

Common interview trap. @NotNull only checks for null — " " passes. @NotEmpty rejects null and empty string but allows " ". @NotBlank is strictest — rejects null, empty, and whitespace-only strings. Use @NotBlank for user-provided text fields.

5

Method-Level Validation

Add @Validated to a @Service class to validate method parameters and return values using constraint annotations directly on method params (e.g., @NotNull Long id). Violations throw ConstraintViolationException, not MethodArgumentNotValidException.

6

Validation Groups

Define marker interfaces as groups (e.g., interface OnCreate {}, interface OnUpdate {}). Apply on constraints: @NotNull(groups = OnCreate.class). Use @Validated(OnCreate.class) in the controller to select which constraint group to activate per endpoint.

7

Structured Error Response (RFC 7807)

Spring Boot 3 introduced ProblemDetail (RFC 7807 Problem JSON format) as the standard error response object. Use it in your @ControllerAdvice to return machine-readable, structured error responses with type, title, status, detail, and custom extension fields like violations.

/* 1. DTO with JSR-380 constraints */
import jakarta.validation.constraints.*;

public record CreateUserRequest(

    @NotBlank(message = "Name is required")
    @Size(min = 2, max = 50, message = "Name must be 2–50 characters")
    String name,

    @NotBlank @Email(message = "Valid email required")
    String email,

    @NotBlank
    @Size(min = 8, message = "Password must be 8+ characters")
    @Pattern(regexp = ".*[A-Z].*", message = "Password needs at least one uppercase")
    String password,

    @Min(18) @Max(120)
    Integer age
) {}

/* 2. Controller — @Valid triggers validation */
@RestController
@RequestMapping("/api/users")
public class UserController {

    @PostMapping
    public ResponseEntity<UserResponse> create(
            @Valid @RequestBody CreateUserRequest req) {
        // Guaranteed: all constraints passed at this point
        return ResponseEntity.status(HttpStatus.CREATED)
                             .body(userService.create(req));
    }
}

/* 3. Global error handler — shapes validation errors into clean JSON */
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Map<String, Object>> handleValidation(
            MethodArgumentNotValidException ex) {

        Map<String, String> errors = ex.getBindingResult()
            .getFieldErrors()
            .stream()
            .collect(Collectors.toMap(
                FieldError::getField,
                FieldError::getDefaultMessage
            ));

        return ResponseEntity.badRequest().body(Map.of(
            "status", 400,
            "violations", errors
        ));
    }
}

/* 4. Custom constraint — @UniqueEmail */
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = UniqueEmailValidator.class)
public @interface UniqueEmail {
    String message() default "Email already registered";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

@Component
public class UniqueEmailValidator implements ConstraintValidator<UniqueEmail, String> {

    private final UserRepository userRepo;

    public UniqueEmailValidator(UserRepository userRepo) {
        this.userRepo = userRepo;
    }

    @Override
    public boolean isValid(String email, ConstraintValidatorContext ctx) {
        if (email == null) return true; // Let @NotBlank handle null
        return !userRepo.existsByEmail(email);
    }
}

7. Senior Developer Answer

"I implement validation as a declarative contract on DTOs using JSR-380 annotations, never in service layers. In controllers, @Valid on @RequestBody triggers Hibernate Validator automatically — any failure throws MethodArgumentNotValidException which my global @RestControllerAdvice catches and shapes into a clean 400 response with field-level error messages.

For the @Valid vs @Validated question: I use @Valid at the controller boundary for standard bean validation, and @Validated when I need validation groups — for example, a 'name' field might be optional on update but required on create. I define marker interfaces as groups and activate them per endpoint.

For cross-field or database-level business rules like unique email checks, I write custom ConstraintValidator implementations that Spring treats as beans — so I can inject a repository directly into the validator for a DB existence check. This keeps service layer clean of defensive validation code."
